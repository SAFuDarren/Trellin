# 架构方向与设计决定

[English](architecture.md) · 简体中文

Research Multiplier 的长期目标是**科研协同框架与科研 AI 系统**：一个组的研究者和 AI agent 在同一个工作区里提出问题、产出证据、互相审阅，并且始终知道哪些结论可信、凭什么可信。Lean 形式化证明是第一个、也是验证最强的场景，但不是唯一场景。

这份文档记录已经确定的方向，以及还在等研究者决定的问题。[路线图](roadmap.zh-CN.md)把它拆成带验收标准的分阶段任务，[工程与项目管理](engineering.zh-CN.md)说明具体怎么做。新代码按「已定」部分写；碰到「待定」部分，先问再做。每条决定带编号，提交说明和代码评审里可以直接引用，例如「按 A3」。

状态说明：**已定**＝照此执行；**待定**＝需要决定，暂时不要写死。

## A. 分层与边界

### A1 五层结构（已定）

| 层 | 负责什么 | 例子 |
| --- | --- | --- |
| 研究内核 | 领域无关的研究记录和规则 | 结论、依据、证据、审阅、影响分析、任务、身份、事件 |
| 插件 | 某个领域或某种验证方式的具体做法 | Lean 验证器、网络流证书检查器、可复现运行、文献来源 |
| 协同 | 多人和多台机器一起工作 | 工作区、成员与角色、任务指派、收件箱、运行环境接入 |
| AI 系统 | agent 执行研究任务 | 文献调研、提出假设、尝试证明、分析数据、可复用的研究流程 |
| 入口 | 人和 agent 怎么使用系统 | CLI、HTTP API、网页工作台、MCP 服务 |

依赖方向只能向下：插件依赖内核的接口，内核不导入任何插件；入口层只调用内核和插件提供的函数。

### A2 业务逻辑只写在一处（已定）

CLI 处理函数、HTTP 处理函数、网页前端都只做参数解析和展示。读写研究记录的逻辑放在 `workflows/`（以及将来的内核模块）里的函数中，CLI 和 API 调用同一个函数。例：审阅收件箱的查询在 `research_review.inbox()`，`review inbox` 命令和工作台的 `/api/inbox` 都调用它。

### A3 Lean 是插件，不是内核（已定，分步迁移）

新代码不得把 Lean 当成唯一情况：

- 内核层的表、函数和接口不出现 `lean`、`lean-core` 之类的名字。
- Lean 特有的概念（Lean 陈述、证明义务、归约、Mathlib 版本）属于 Lean 插件。
- 界面上，Lean 证明结构是依赖图的一种视图；通用视图是「结论—证据」图。

现状：SQL 迁移里有 28 处写死的 `'lean-core'`，大量 `lean_*` 表和函数直接挂在 `rm` schema 下。这些不需要一次改完，但新增功能不再扩大这种耦合，改到相关代码时顺手往插件边界迁移。

## B. 研究内核

### B1 内核概念（已定）

| 概念 | 含义 |
| --- | --- |
| 研究问题 | 研究者想回答的问题，可以先模糊，再逐步澄清 |
| 结论 | 冻结后的明确陈述和适用范围。冻结后内容不变，修改会产生新版本 |
| 依据 | 结论所依赖的、带版本的条目：假设、定义、已有结果、数据集、文献 |
| 产出 | 证明文件、代码、数据、notebook、论文等文件，按内容哈希存储 |
| 证据 | 某次验证或审阅对某个结论给出的判断，记录用到的依据版本、产出哈希和验证器版本 |
| 验证器 | 产生证据的程序或流程，自身带身份、版本和源码指纹 |
| 审阅 | 有身份的研究者对证据或结论做出的决定，带理由 |
| 影响分析 | 依据被撤回或改版时，把用到它的证据和结论标为待重验 |
| 任务 | 指派给人或 AI 的一项工作，例如「尝试证明」「复现这个实验」「审阅这条证据」 |
| 事件 | 每一次状态变化的不可变记录（见 B5） |

现有实现已经具备其中大部分：冻结的 claim、带版本的 formal item、evidence 与 review、`verification_basis_use` 与重验传播。泛化的工作主要是把它们和 Lean 拆开，而不是从头重写。

### B2 可信等级（原则已定，等级划分待定）

每条结论都明确标出自己当前的可信程度，这是本产品和通用 agent 协作工具的根本区别。原则：

- 可信等级由**验证器或审阅**决定，不由产出者自己声称。
- **AI 的产出一律以「提议」身份进入**，可信等级最低；只有经过验证器检查或人工审阅才能升级。AI 不能批准、不能升级任何结论，包括它自己的。
- 依据被撤回时，可信等级随影响分析自动下降。

初步的等级（从强到弱）：形式化证明、确定性检查（证书、反例）、可复现（代码加数据加环境，重跑结果一致）、人工审阅、有文献出处、仅 AI 生成。具体划分和先后顺序见待定问题 Q5。

### B3 类型可以注册，不写死在数据库里（已定）

证据类型、领域、验证器、依据条目的种类都通过注册来增加，带 schema 版本。不再在 SQL 的 `CHECK (kind IN (...))` 里新增领域相关的枚举值；目前有 20 个 SQL 文件包含这类列表，后续逐步收拢。数据库只约束通用的不变量，例如「每条证据必须引用一个已注册的验证器版本和它用到的依据版本」。

### B4 身份（已定）

每一次写操作都记录**已认证的用户 ID**。本机模式下初始化时创建一个本地用户，所有操作记在这个用户名下；多人模式下来自登录身份。现在的 `actor_ref` 自由文本（SQL 里约 220 处）保留为显示名，不再作为身份依据。新的写接口一律从会话取身份，不接受调用方自报的名字。

### B5 事件日志（已定）

每一次状态变化追加一条事件：工作区、操作者、事件类型、对象、内容摘要、时间。实时推送、审计、多端同步、通知都从事件日志派生，不各自另起一套记录。现有的各类 ledger 保留，逐步统一到这一机制上。

### B6 PostgreSQL 是唯一的记录系统（已定）

研究记录只以 PostgreSQL 为准，关键不变量继续由数据库约束和函数保证，这是可审计性的基础。插件自己的表放在插件自己的 schema 里，内核表留在内核 schema。文件类产出按内容哈希存在工作区或对象存储中，数据库只存引用和哈希。

### B7 验证器可复现（已定）

验证器必须能被精确重现：记录身份、版本和源码指纹。`_pinned/` 目录正是为此存在的，它保存已记录指纹对应的验证器、适配器和历史评估源码；`_compat/` 为这些源码提供原有的导入入口。新的验证器沿用同样的原则，不能随意改动已经产生过证据的验证器源码。

## C. 插件

### C1 插件以独立进程运行（已定）

系统启动插件进程，通过工作目录里的 JSON 文件交换输入和输出，标准输出和标准错误只作为日志（具体协议见[接口契约](interfaces.zh-CN.md#6-插件协议-v1)）。这样插件可以用任何语言写：Lean、R、Julia、MATLAB、C++、Fortran 都可以接入，调用 Lean 的现有方式就是这个模式。Python SDK 只是为写 Python 插件的人提供便利，不是要求。

### C2 插件清单（已定，格式待细化）

每个插件附一份清单：名称、版本、类型（验证器、领域包、工具、来源）、入口命令、运行环境要求、输入输出 schema、需要的权限（例如是否联网、是否调用外部模型）。

### C3 每个插件独立环境（已定）

不同学科的依赖差别很大，不能装进同一个 Python 环境。每个插件用独立的环境运行，由 uv 单独创建，或者直接跑在容器里。

### C4 对外提供 MCP 服务（已定）

验证器和研究工具通过 MCP 暴露，让外部 agent（Claude Code、Codex 等）可以直接调用。经 MCP 产生的结果同样按 B2 以「提议」身份进入。

## D. 协同与运行

### D1 一套 API，本机和云端共用（已定）

本机工作台和组内服务器使用同一套 HTTP API，以 OpenAPI 定义契约，并遵守[接口契约](interfaces.zh-CN.md)。前端的类型从契约生成。本机模式就是只有一个用户的同一个服务。

### D2 长任务走队列，由 worker 执行（已定）

Lean 核验、模型调用、实验运行等耗时工作一律作为任务进入数据库队列，由 worker 领取执行。worker 以常驻进程运行，主动连接服务器，用令牌认证并定期报心跳；组员的电脑也可以作为运行环境接入。本机模式下 worker 跑在同一台机器上，流程不变。

### D3 实时更新从事件派生（已定）

先用 PostgreSQL 的 LISTEN/NOTIFY 加服务器推送事件（SSE）；只有出现双向实时需求时再引入 WebSocket。

### D4 数据离开工作区需要授权（已定）

任何把研究内容发给外部服务（外部模型、云端工具）的操作，都需要事先授权，并记录是谁授权的。现在「发给 Codex 前要确认」的规则推广为按工作区、按课题、按人配置的权限。

### D5 多工作区共用一个数据库，用行级安全隔离（已定）

一次部署使用一个 PostgreSQL 数据库。每条属于工作区的记录都带工作区 ID，由行级安全策略保证一个工作区看不到另一个工作区的数据；内核函数和视图都在当前会话的工作区范围内执行。本机模式是只有一个工作区的同一种结构。

现状是每个项目绑定自己的数据库（`bind-workspace`）。迁移时需要给内核表加工作区 ID 和行级安全策略，并提供把现有单项目数据库导入共享数据库的工具；在那之前，单项目数据库继续可用。

### D6 先支持各组自部署，为以后的托管服务留好空间（已定）

当前目标是一个研究组在自己的服务器上部署。设计上不假设「一次部署只服务一个组织」：身份、工作区、权限和计量都按多组织可扩展的方式建模，以便以后提供我们运营的托管服务时不用改数据模型。

## E. 技术选型

### E1 语言（已定）

- 内核、编排、插件 SDK：Python。科研生态集中在 Python，研究者写插件最方便。
- 前端：React 加 TypeScript，用 Vite 构建，源码放在 `web/`。编译后的文件随 Python 包发布，用户不需要安装 Node。
- 插件：任意语言（C1）。
- Go 等其他语言只用于将来确有需要的独立组件（例如高并发实时网关），不用于重写核心。

### E2 Python 工程约束（已定）

- 内核代码开启严格类型检查（pyright 或 mypy）。
- 对外数据结构用 schema 定义（JSON Schema 或 OpenAPI），不靠约定。
- 纯 Python 的重计算循环改用 numpy、现成求解器，或做成外部插件。
- API 服务用异步 IO，worker 用多进程。

### E3 安装与分发（已定）

- 基础安装保持零依赖。
- 个人使用：`uv tool install research-multiplier`。
- 组内服务器：Docker Compose，包含 PostgreSQL（含 pgvector）、API 服务，以及预装 Lean 和 Mathlib 缓存的 worker。
- 桌面应用（以后）：打包 Python 运行环境，用户感觉不到 Python 的存在。

### E4 测试放在仓库里，在 CI 中运行（已定）

测试和代码放在同一个仓库，每个 PR 在 CI 中运行，安装包不包含测试。现有按版本单独保存的外部回归套件逐步并入仓库；涉及大体积固定数据或 Lean 项目的部分可以继续单独存放，但运行入口和断言在仓库里。

### E5 界面术语（已定）

内部概念面向 agent，可以精确而密集；界面只暴露少数概念，告诉用户现在是什么情况、需要做什么。

### E6 界面语言（已定）

界面默认英文，并提供完整的中文翻译。从迁移到 React 开始，所有面向用户的文字都放在翻译文件里；API 的错误带稳定的错误码，由界面负责翻译。研究内容按输入原样保存，不做自动翻译。

### E7 开放社区，在 GitHub 上管理（已定）

项目以开放社区的方式开发。任务、缺陷和里程碑放在 GitHub Issues 和 GitHub Projects 看板上，里程碑与路线图的阶段一一对应。贡献规则见[工程文档](engineering.zh-CN.md#开放社区)。

### E8 版本号从 1.0.0 继续往后走（已定）

1.0.0 已经公开发布，版本号按语义化版本规则继续往后走，出现不兼容的改动就升主版本号。HTTP API、插件协议和事件内容各自带版本，新接口可以标注为实验性。详见[工程文档](engineering.zh-CN.md#版本与兼容性)。

### E9 许可证与贡献方式（已定）

目标：让个人和机构放心使用、愿意贡献，同时为以后做成产品留下空间。

- **代码许可证：Apache License 2.0**，从下一个发布版本开始生效。它和 MIT 一样宽松，另外有明确的专利授权和专利报复条款，这是公司和高校最看重的；也和 Lean 4、Mathlib 的许可证一致。1.0.0 及更早的版本继续以 MIT 提供。`LICENSE` 文件里放未经修改的许可证原文，版权声明放在 `NOTICE` 文件里。
- **贡献方式：开发者原创声明（DCO）。** 每次提交都带 `Signed-off-by`（用 `git commit -s`）。贡献按 Apache-2.0 进来，也按 Apache-2.0 出去（Apache-2.0 第 5 条），不需要另签协议。
- **名称与标志：** 不在代码许可证范围内（Apache-2.0 第 6 条）。`TRADEMARKS.md` 允许任何人说明自己的作品使用或扩展了 Research Multiplier，但要求分叉版本和托管服务另起名字。这样不限制代码，也能保护品牌。
- **文档**跟随代码许可证。**用户的研究数据、证明和结论**归用户自己所有，不受软件许可证约束。**插件**可以自选许可证，并在清单里写明。
- **如果以后做成产品：** 收费功能作为独立的扩展发布，使用自己的许可证（开放核心模式），放在明确分开的目录或仓库里。Apache-2.0 的核心部分绝不依赖它们，也不需要为此更换许可证。
- **以后想改方向：** 以后的版本如果改用别的许可证（比如 AGPL 加双重授权，或者源码公开类许可证），只能针对版权人同意的代码。合并第一个外部贡献之前，版权人只有维护者自己；之后，每一位代码仍在仓库里的贡献者都要同意，否则就得重写他们的代码。合并第一个外部 PR 之前，再最后确认一次这个选择。

这是项目层面的决定，不构成法律意见；正式依赖许可证和商标文本之前，请律师审阅。

## F. 迁移顺序

详细任务和验收标准在[路线图](roadmap.zh-CN.md)里，这里只列摘要。

1. 整理并提交现有改动（agent 指南、工作台、0069–0071 迁移、分区页接口），把测试放回仓库并接入 CI（E4）。
2. 按 B4 引入本地用户身份，新写接口改从会话取身份。
3. 定义 API 契约，前端迁到 TypeScript，完成功能栏分区页面。
4. 设计内核与 Lean 插件的边界（A3、B3），先拆新功能涉及的部分。
5. 实现事件日志和 SSE（B5、D3）。
6. 引入工作区 ID 和行级安全（D5），做 worker 接入协议和组内服务器部署（D2、E3）。
7. 用第二个场景检验内核抽象（见 Q6）。
