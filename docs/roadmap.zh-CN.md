# 路线图与验收标准

[English](roadmap.md) · 简体中文

这份路线图把[架构决定](architecture.zh-CN.md)拆成阶段执行。每个任务写明由谁负责、落实哪几条决定，以及验收标准：标准全部满足才算完成。一个阶段的所有任务都达标，并且满足该阶段的出口标准，这个阶段才算完成。

负责方：

- **后端**：Python、SQL 和服务端，由维护者负责。
- **前端**：React 界面，由维护者与 Claude 合作完成。
- **维护者**：项目和社区层面的决定。

每个任务对应一个 GitHub issue，归入所属阶段的里程碑。issue 里写明验收标准，并引用相关决定的编号。具体流程见[工程与项目管理](engineering.zh-CN.md)。

同一阶段内的任务可以并行，除非写明了依赖。

---

## 公开条件

以下条件全部满足之前，仓库保持私有；满足后转为公开（E7），并开启分支保护（P0.4）。

- P0 全部完成：测试移进仓库（P0.2）、开发工具（P0.3）、社区基础（包括里程碑和标签，P0.4）、依赖扫描（P0.5），以及回归测试和交接测试这两项压力测试（P0.6）。
- React 界面实现与现有工作台的功能对齐（P1.4），功能栏和各分区页面完成（P1.5）。
- 用当前代码在 Apache-2.0 下重新构建 1.0.0 发布，删除旧的 MIT 草稿发布。
- 公开前做一次工程审计，没有未解决的 P0 发现。

## P0 打基础（当前）

目标：留下一个干净、有测试覆盖的基线，后续工作都从这里开始。

### P0.1 提交现有改动（后端）

验收标准：

- 工作区没有未提交的改动。现有改动分成以下几次独立提交：
  1. agent 指南；
  2. 工作台后端（依赖图、运行记录、模型意见、迁移 0069–0071）；
  3. 工作台前端；
  4. 分区页接口，连同收件箱和模型预算的重构；
  5. 架构、路线图和工程文档。
- 迁移 0069–0071 既能在空数据库上执行，也能从 0068 升级上来。
- 每次提交都能通过 CI 的安装包冒烟测试。
- 在同一个数据库上，`research-multiplier review inbox` 的输出和重构前一致。

### P0.2 测试放回仓库并接入 CI（后端；E4）

验收标准：

- 新建 `tests/` 目录，用 pytest 标记至少区分三条测试线：`offline`、`postgres`、`lean`。
- `uv run pytest -m offline` 不需要数据库和 Lean，五分钟内跑完。
- `postgres` 线在每个 PR 上运行，CI 为它启动一个用完即弃、装有 pgvector 的 PostgreSQL。`lean` 线定时运行，并在发布前运行。
- 构建出的安装包不含测试文件，CI 会列出安装包内容来检查。
- 外部验证包里的用例全部移植进仓库，或者至少把运行入口和断言放进仓库。只有体积很大的固定数据可以继续放在外面，按哈希下载。
- 工作台服务端有以下测试：
  - session 令牌、Host 和 Origin 校验；
  - CSP 和其他安全响应头；
  - 每个 `/api` 接口在测试数据库上的行为；
  - `POST /api/review` 和 `POST /api/guidance` 的输入校验。

### P0.3 开发工具基线（后端）

验收标准：

- 仓库提交 `uv.lock`，`uv sync` 可以直接建好开发环境。
- CI 运行 `ruff check` 和 `ruff format --check`。已有的问题可以先记在一份基线清单里，这份清单只能缩小，不能扩大。
- CI 运行 `pyright`，不能有错误：整个包用基础模式，新写的内核模块用严格模式。
- 为 Python 依赖、GitHub Actions 开启 Dependabot 或同类工具；P1.4 之后把 npm 依赖也加进来。

### P0.4 社区基础（维护者）

验收标准：

- 在合并第一个外部 PR 之前，CI 强制检查 DCO 签名（E9），并最后确认一次许可证。
- 仓库里要有：`CODE_OF_CONDUCT.md`；`SECURITY.md`（写明私下报告漏洞的渠道）；issue 和 PR 模板；`CODEOWNERS`。
- `CONTRIBUTING.md` 写明提交前检查清单，并指向架构决定。
- 在 GitHub Projects 建好看板和 P0–P6 里程碑，标签按[工程文档](engineering.zh-CN.md#issue-与计划)的定义设置。
- `main` 开启分支保护：Checks、Tests、DCO 都通过，并经代码负责人批准，才能合并。这需要仓库公开，时间按公开条件来定（审计发现 A-202611-01）。

### P0.5 依赖与漏洞扫描（后端）

验收标准：

- `.github/dependabot.yml` 覆盖 pip、GitHub Actions，P1.4 之后加上 npm。
- CI 对安装好的包（含额外依赖组）运行 `pip-audit`。发现已知漏洞时检查失败，除非有一条写明理由和到期日的忽略记录。
- 工作流里的 GitHub Actions 固定到提交 SHA，由 Dependabot 负责更新。

### P0.6 回归与交接压力测试（维护者）

验收标准：

- [工程审计](audits/README.zh-CN.md)的压力测试 4：按维护者提供的审计方案逐个注入故障，每个都要让某项离线测试失败。漏掉的故障要补上新测试。
- 压力测试 6：一个全新的 agent 只凭仓库内容完成一个普通任务，不需要额外解释就能遵守 `AGENTS.md`。它漏掉的每条规则，要么补进 `AGENTS.md`，要么改由 CI 强制。
- 两项结果都记录到下一次审计里（审计发现 A-202611-13）。

P0 出口标准：新贡献者克隆仓库后，运行 `uv sync` 和 `uv run pytest -m offline` 能通过；提交 PR 后，能看到所有必需检查都在 CI 中运行。

## P1 地基

目标：用户身份、有契约的 API、实时更新，以及新的 React 界面和功能栏各分区。

### P1.1 本地用户身份（后端；B4）

验收标准：

- 新增用户表。`init-workspace` 创建一个本地用户，并把用户 ID 写进工作区配置；已有项目通过 `bind-workspace` 补建。
- 新的写函数接收用户 ID。现有写函数改为也接收用户 ID，`actor_ref` 只作为显示名保留。
- 工作台的 session 对应到这个本地用户。`POST /api/review` 不再接受 `actor` 字段。
- 测试覆盖两点：无法确定用户时写操作必须失败；记录下来的用户与当前 session 一致。

### P1.2 API 契约（后端；D1）

验收标准：

- 工作台的所有接口挂在 `/api/v1` 下。旧的 `/api` 接口保留到 React 界面完成切换（P1.4）后再删除。
- 仓库里有一份 OpenAPI 3.1 文档。它可以手写并作为唯一依据，也可以由代码生成，但必须在 CI 中生成。
- 有测试确认：每个实际提供的接口都写进了文档，并且在测试数据库上返回的数据都符合文档。
- 错误统一使用 `{"error": {"code": "...", "message": "..."}}` 格式。`code` 是稳定的标识，界面按它翻译；`message` 是英文的兜底说明。
- `pnpm gen:api` 重新生成 TypeScript 类型。生成结果与已提交的文件不一致时，CI 失败。
- 每个响应都带 `X-Request-Id`。服务端日志采用结构化格式（每行一个 JSON 对象），记录请求 ID、路由、状态码和耗时，绝不记录研究内容（审计发现 A-202611-10）。

### P1.3 事件日志与实时更新（后端；B5、D3）

验收标准：

- 新增事件表，记录工作区、用户、事件类型、对象和摘要。每个写流程在同一个事务里追加事件；有测试逐个检查所有写函数。
- 写入事件时发出 `NOTIFY`。`GET /api/v1/events` 以服务器推送事件（SSE）的方式持续输出，断线后可以按 `Last-Event-ID` 续传。
- 在本机上，事件从写入到传给已连接的客户端不超过一秒。
- 事件摘要不包含凭据和数据库连接串。研究内容只在该对象本来就对同一工作区可见时才出现。

### P1.4 React 界面，功能与现有工作台一致（前端；E1、E6）

依赖 P1.2 生成的类型；在 P1.2 完成前，可以先对接现有接口开工。

验收标准：

- `web/` 是一个 pnpm 包（React、TypeScript、Vite）。`pnpm build` 把构建结果写进 Python 包的资源目录，随 Python 包发布，用户不需要安装 Node。
- 服务端的 CSP 不变：没有内联脚本和内联样式，也不加载外部资源。
- 现有工作台的功能全部保留：
  - 课题列表和搜索；
  - 依赖图的平移、缩放和适合窗口；
  - 全局图可以移动、可以调整大小；
  - 分隔条可以拖动，尺寸会被记住；
  - 审阅队列和节点详情；
  - 假设影响预览；
  - 与模型的对话，包括发给 Codex 前的两步确认；
  - 浅色和深色主题。
- 所有面向用户的文字都来自翻译文件：默认英文，可切换中文。有 lint 规则禁止在 JSX 里直接写文字。
- 逻辑部分用 Vitest 测试；上面的功能清单用 Playwright 在测试服务器上逐项测试，并在 CI 中运行。
- 首次加载的 JavaScript 压缩后不超过 300 KB。

### P1.5 功能栏与各分区页面（前端）

依赖 P1.4。数据来自 P0.1 提交的分区接口，P1.2 之后改走 `/api/v1`。

验收标准：

- 功能栏和以下分区页面与确认过的效果图一致：审阅、课题、定理库、对话、团队（运行环境、Agent、用量、任务队列）、推进。
- 在测试项目上，批准和退回证据能完整跑通，功能栏上的待审阅数字随之更新。
- 每个页面都有加载中、无数据、出错三种状态；只用键盘就能完成所有操作；用 axe 检查没有严重问题。
- 页面只显示 API 返回的数据，前端不自己编造数据，例如后端并未记录的用量上限。

### P1.6 界面实时更新（前端；D3）

依赖 P1.3 和 P1.4。

验收标准：

- 界面订阅 `/api/v1/events`，收到事件后刷新受影响的部分。轮询只在连接断开时作为后备。
- 在命令行里做的修改，两秒内出现在已打开的工作台上。

### P1.7 架构结构图与分层检查（后端；A1、A2、A3）

验收标准：

- 在 `docs/` 里发布当前各包的依赖图，由脚本自动生成，保证和代码一致。
- CI 里运行 import-linter（或同类工具），检查以下规则：
  - `cli` 和 `workbench` 可以导入 `workflows`，但不能互相导入对方的内部实现；
  - `workflows` 不能导入 `cli`；
  - 新的内核代码不能导入 Lean 专用模块。
  已有的违规写进一份清单，清单只能缩小。
- 审计时可以借助这张图，统计最近 PR 的变更影响范围（审计发现 A-202611-05）。

### P1.8 发布恢复演练（维护者）

验收标准：

- 在一个临时项目上：先装上一个发布版本并备份，升级到候选版本，再用上一个版本把备份恢复到一个新数据库。两步都成功，并且记录一致。
- 把这些步骤写进[发布准备](release.md)，每次发布都记录演练结果（审计发现 A-202611-09）。

P1 出口标准：一位研究者日常工作都在 React 工作台里完成；每一次写操作都能对应到具体用户；每个 API 响应都在契约覆盖之内。

## P2 内核与插件

目标：把领域无关的内核从 Lean 中拆出来，开放插件接口。

### P2.1 类型注册（后端；B3）

验收标准：

- 为证据类型、验证器、领域、依据条目类型建立注册表，每项带 schema 版本。现有类型通过迁移登记进去。
- CI 中的 lint 规则：在指定的截止版本之后，迁移里不得再出现新的 `kind IN (...)` 列表或新的 `'lean-core'` 字面量。已有的写法列入允许清单。
- 所有回归测试线结果不变。

### P2.2 内核与 Lean 的边界（后端；A3）

验收标准：

- 在架构文档里补一份设计说明，把现有的每张表、每个视图、每个函数归为内核或 Lean 插件。
- 新增的 Lean 专用对象放在单独的 schema 里。内核的证据接口不再要求 Lean 字段。
- 依赖图 API 返回通用的「结论—证据」图，Lean 证明结构作为可选视图。

### P2.3 插件协议与运行器（后端；C1–C3、B7）

验收标准：

- 插件清单、请求和响应格式都以带版本的 JSON Schema 发布。
- 用 `research-multiplier plugin list | install | check` 管理插件。每个插件在自己的环境里运行（uv 环境或容器），有时间和内存上限，清单没有声明联网就不能联网。
- 插件产生的证据记录插件名称、版本和源码指纹。
- 三个参考插件都要通过同一套一致性测试：包装成插件的 Lean 验证器、一个 Python 示例、一个非 Python 示例（例如 R，或编译型语言写的程序）。

### P2.4 MCP 服务（后端；C4、D4）

验收标准：

- `research-multiplier mcp` 通过标准输入输出提供服务。它提供的工具包括：读取结论、定理库、依赖图、收件箱，以及运行验证器。
- 结果只以提议身份进入（B2），调用遵守工作区的外部数据权限（D4）。
- CI 用 MCP 客户端连上这个服务，逐个调用所有工具。

### P2.5 可信等级（后端和前端；B2）

依赖 Q5 先定下来。

验收标准：

- 每个结论都显示一个可信等级。等级根据证据和审阅计算得出，不允许手工填写。
- 撤回一条依据后，依赖它的结论等级随之下降；有测试覆盖。
- 界面上显示等级，以及得出这个等级的原因。

P2 出口标准：一个在本仓库之外、用 Python 以外的语言写的验证器产生的证据，可以被内核记录、在界面上显示，全程不需要改内核代码。

## P3 组内服务器

目标：一个研究组共用一套部署（D5、D6）。

### P3.1 工作区隔离（后端；D5）

验收标准：

- 每张属于工作区的表都有非空、带索引的工作区 ID 列。行级安全已开启，并设为强制生效。
- 每个会话通过 `SET LOCAL` 设定当前工作区。
- 每张表都有隔离测试：从别的工作区读不到任何行，写入会失败。
- 提供导入工具，把单项目数据库迁进共享数据库，并核对行数和内容哈希。
- 准备 100 个工作区的测试数据，主要页面的查询仍然走索引。

### P3.2 账号、登录与角色（后端；B4、D6）

验收标准：

- 数据模型包括用户、组织、工作区和成员关系，角色分为 owner、admin、member、viewer。权限矩阵写成文档，并有测试覆盖。
- 支持邮箱验证码登录和 OIDC 登录。
- CLI 和 worker 使用个人访问令牌：限定权限范围、会过期、可以吊销，数据库里只存哈希。
- 登录、创建令牌、角色变更都会写入事件。

### P3.3 Worker 接入协议（后端；D2）

验收标准：

- `research-multiplier worker connect --server URL` 用令牌认证，只主动向外发起 HTTPS 连接，每 15 秒报一次心跳。
- 每个 worker 上报自己的能力：Lean 版本、Mathlib 哈希、可用的模型 CLI、已装插件。服务器只派给它能执行的任务。
- worker 被强行结束后，它手上的任务在租约到期后释放，交给别的 worker 重试。测试中启动两个 worker，在执行中途结束其中一个。
- 团队页面显示每个运行环境的状态、能力和当前负载。

### P3.4 外部数据权限（后端；D4）

验收标准：

- 权限可以按工作区、按课题、按人配置。每次对外调用都先检查权限，并记录是谁授权的。
- 有测试确认：被拒绝的调用不会真正发出去。
- 如果以后加入使用统计，默认关闭，只有管理员手动开启才生效。

### P3.5 部署（后端；E3）

验收标准：

- 在一台干净的 Linux 主机上，`docker compose up` 能启动三部分：带 pgvector 的 PostgreSQL、API 服务、预装 Lean 和 Mathlib 缓存的 worker。健康检查全部通过。
- 文档写明备份、恢复、升级的命令。升级时自动执行迁移；有测试从上一个发布版本升级上来。
- 写明硬件要求和 TLS 配置方法。

### P3.6 协同界面（前端）

验收标准：

- 界面上有以下页面：登录、成员与角色、运行环境、令牌、权限。
- 按用户的角色隐藏或禁用相应操作；服务端同样按角色校验，不只依赖界面。

P3 出口标准：一个组的三个人共用一台服务器，各自登录；两位成员的电脑作为 worker 接入；一个人做的审阅，其他人实时看到；任何工作区都读不到别的工作区的数据。

## P4 第二个场景

目标：证明内核真的与领域无关（对应 Q6，建议的场景是「计算实验可复现」）。

验收标准：

- 一个「可复现运行」插件记录代码版本、数据哈希和运行环境，并产生证据。
- 在另一个 worker 上重跑，得到与记录一致的输出，证据被接受。
- 数据集换了新版本后，依赖它的结论被标为待重验。
- 内核不需要任何 Lean 相关的修改。这个阶段如果需要改内核，先写设计说明，对照 A1–B7 评审。

## P5 AI 系统

目标：agent 在内核规则的约束下完成研究任务。

验收标准：

- 任务可以指派给人，也可以指派给 agent。agent 的每次运行都记录模型、提示词版本、输入、费用和输出；所有输出一律以提议身份进入。
- 可复用的研究流程（技能）带版本，可以挂到任务上。
- 推进策略推广到各类任务，支持定时触发和条件触发。
